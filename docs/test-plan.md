# 测试计划 · @grapecity-software/dsh-spreadjs-driver 1.0

`pnpm run ci`（worker-smoke + **export-integrity** + tool-smoke + live/client/confinement + pack 校验 + 从 pack 冒烟）是无 LLM 的
**回归网**；`docs/e2e-checklist.md` 是发版前的**人工验收**。本文是两者的补充：按
风险维度穷举用例，标注覆盖状态，未覆盖的留给下一轮。

| 套件 | 校验的是 |
|---|---|
| `test:worker` / `test:tool` | 协议、错误码、全链行为；产物只看**魔数与长度**。worker-smoke 另外钉住引擎生命周期：空闲退出、空闲时不留页面（= 不留窗口）、结束后不留浏览器 |
| `test:integrity` | 产物的**字节**：zip 条目 CRC-32 与尺寸、CJK 字节级一致、公式缓存值、数字格式、xlsx 往返；PDF 字体**真嵌入**（FontFile + 子集前缀）与文本操作符；PNG 真实墨迹与尺寸 |

## 插件侧收尾测试（2026-09-16，不经过模型，直接对 worker 打）

前面各表测的是"模型用得对不对"，这一批反过来查**插件自己**。详见
`D:\sjs-e2e\plugin-tests\RECORD.md`。

| 项 | 结果 |
|---|---|
| 畸形与恶意输入（空/非 JSON/截断/`sheets:[null]`/600 层嵌套/假 xlsx/0 字节 xlsx） | ✅ 每项都有明确错误码，无挂起无崩溃；10 万行×40 列的高压缩比表导出 21 s / 导入 18 s 均成功 |
| **日期与 Excel 序列号往返** | ⚠️ **曾是真缺陷，已修复**：沙箱是独立 vm realm，`new Date()` 造的值 `instanceof Date` 对引擎为假，`setValue(cell, new Date(...))` 被静默写成序列号 0、显示 1899/12/30。修法：把主 realm 的 `Date` 注入沙箱 context；已加 CI 回归。修后三种写法均正确显示并导出为 OADate |
| 浮点精度（`0.1+0.2`、`1/3`、`2^53+1`、`SUM(0.1×10)` 等 8 项） | ✅ 与 Excel 逐项一致，xlsx 往返不变 |
| 错误公式（`#DIV/0!`/`#REF!`/`#N/A`/`#NAME?`/`#VALUE!`） | ✅ 五种错误码与显示文本均保留，含 xlsx 往返 |
| 图表/透视表导出后的 Excel 打开 | ✅ **真实 Excel 16.0 打开无需修复**；图表被认成原生图表（chartType 51）、透视表认成原生 PivotTable |

> 注：这批测试用的是一次性 worker 产物，与 profile 是否安装插件无关；运行期间未留游离进程。（2026-09-20 起运行时改为常驻引擎，本条结论由 worker-smoke 的孤儿断言与 `scripts/audit-browsers.mjs` 继续保证。）

### 常驻引擎的进程卫生（2026-09-20 新增）

引擎现在是常驻进程，浏览器也就是常驻的。**一个没关掉的引擎 = 一个活着的浏览器 =
一个真实窗口**（headless 下不可见，但会出现在系统的窗口列表里，并占 15 个进程 /
150–250 MB），所以"关不掉"从不可见变成了肉眼可见。

复现方式（可随时重跑，也是这一节存在的意义）：

```
node scripts/audit-browsers.mjs --max-concurrent=4 -- pnpm run ci
```

它每 2 s 采样一次存活引擎浏览器数，跑完留 10 s 宽限，**之后还有存活即失败**；并发数
超过上限也失败。单轮 CI 的实测：峰值 1（worker-smoke 的空闲退出用例里会短暂到 2），
命令结束后 0。

## 对照实验 · 装插件 vs 卸插件（2026-09-16）

**为什么做**：验证插件是否真的带来净收益——会不会"不用插件反而更好"。

**方法**：同一提示词、同一批前置文件、同一模型（`deepseek-v4.1-flash`）、`web` profile，
分别在**装插件**与**卸插件**（`uninstall.bat`）两种状态下各跑一次 T1（去重）与 T2（跨文件
合并）。两边的产物都另行独立复核，不采信模型自述。

**⚠️ 时长必须先剥掉用户自己的时间。** 两轮"有插件"的会话里，各有一段 `turn/end` 之后
**完全无事件**的空白（1951 s / 1087 s）——那是模型答完之后用户查看/离开的时间。不剥离
会得出**刚好相反**的结论。

| 指标 | T1 去重（phase 10） | T2 合并（phase 11） |
|---|---|---|
| 模型净耗时 · 有插件 | **276 s** | **328 s** |
| 模型净耗时 · 无插件 | 492 s | 743 s |
| 工具调用 · 有 / 无 | 25 / 39 | 42 / 46 |
| 每步均耗时 · 有 / 无 | 9.0 s / 15.0 s | 8.8 s / 16.7 s |
| 失败次数 · 有 / 无 | 2 / 0 | 6 / 0 |

**为什么无插件反而更慢**：它的**单次工具调用本身就重**——实测 `tool/call → tool/result`
有 121 s、105 s、82 s、65 s 这样的间隔，因为它用 **COM 驱动真实 Excel**（打开/另存/关闭）
并**手工解包、改写、重打包 xlsx 的 OOXML XML**。插件的调用只是起一个一次性 worker（数秒）。

**结论**：插件在**速度（1.8–2.3×）、调用数、主动性**上均占优，**不存在"不用反而更好"**。

### 产物正确性：各自口径下都正确

| | 有插件 | 无插件 |
|---|---|---|
| T1 | 16 行（用户选的"忽略备注"口径） | 18 行（"整行 17 列全同"口径） |
| T2 | 207 行（按用户选择去重） | 214 行（未去重） |

独立复核：无插件 T1 全字段重复 0（源 25 行 → 唯一 18 行）；无插件 T2 = 189 + 25 = 214 ✓。

### 差异的性质

- **偏插件 · 主动性**：T2 无插件那轮**没有发现文件1 的 5 组重复行**，只问了排版
  （"两文件表头完全一致，可以直接纵向拼接"）；有插件那轮**主动报出**"5 组完全重复、多出
  7 行"并询问是否处理。所以 214 vs 207 不是对错之分，而是**有没有主动发现数据质量问题**。
- **偏插件 · 环境依赖**：无插件路径要求本机装有 Excel；实测还**留下一个 EXCEL 进程**
  需要自行 kill 掉。插件的 worker 是自清理的。
- **偏无插件 · 零失败**：有插件两轮各 2 / 6 次失败，全部是模型**猜 SpreadJS API**
  （`conditionalFormats.all`、`getDataValidations` 都不存在）。这不是插件缺陷，但说明
  "不确定就查文档"这一步仍会被跳过，值得继续强化。

> 复现方式：`uninstall.bat` 卸载 → 新开会话跑提示词 → `build.bat` 还原。

## 已知限制（非缺陷，写入文档即可）

- 只支持 `.xlsx / .csv / .ssjson`；旧 `.xls` 需先另存。
- 未授权标记（预期，且**刻意不去清除**）：png 画布带 `Evaluation Version` 戳记；导出的 `.xlsx` 多一张同名工作表（由引擎在导出时注入）；`.pdf` 与 `.csv` 没有。详见 SKILL。
- 截图文本统一重绘为单一 CJK 字体，逐格字体差异被拉平（仅影响图片）。
- 纯文本模型路由下 png 进不了上下文，`read_image` 同样会拒绝。
- worktree 仅 `create`/`list`，无 `merge`/`discard`。
